How it works

One loop, every task. State lives in files (tasks.json, specs/, history.md), not in chat.

  1. You pick or describe a task.
  2. The agent writes a concise spec: requirements, design, tasks. No code yet.
  3. You review and approve the spec in one interactive page.
  4. The agent implements only what was approved.
  5. Tests and validation run.
  6. A reviewer checks that requirements, design, code and tests line up.
  7. Affected docs are updated. A task with stale docs is not done.
  8. The task is marked done, or sent back for correction.

Review specs in the browser

One page per feature. No Node or Python needed.

  1. Render it: sh scripts/render-spec.sh specs/<feature-slug>/ (Windows: scripts/render-spec.ps1). It writes specs/<feature-slug>/spec.html.
  2. Open it. The overview shows at a glance and needs your decision; each document has its own tab. Light and dark themes.
  3. Per item: Accept, Change, Reject, Answer or Comment. Then approve or request changes.
  4. Save feedback.md (or copy it) and tell the agent “read the feedback”. It updates the markdown, which stays the source of truth, and re-renders the page.

Install in one prompt

  1. Copy this kit folder into your project root: my-project/sdd-onboarding-kit/.
  2. Open your harness in my-project/ and run:
Read `sdd-onboarding-kit/instructions.md` and configure this repository to use Spec Driven Development with this harness. Ask me all necessary questions before making project-specific decisions.

The agent confirms your harness, inspects the repository, asks the questions in questions.md and generates a project-specific harness in that harness's own layout.

Short on time? Accept the recommended defaults in one answer. Only the project-specific questions remain: commands, protected files, SDD scope.

What you get

Installed by default, adapted to your project.

AGENTS.md

Short project instructions read by every harness. Claude Code gets a two-line CLAUDE.md import stub.

Five roles

Leader, spec-author, implementer, reviewer, documenter, in your harness's agent format.

SDD workflow skill

Workflow, state machine, review checklist, concise spec templates with word budgets.

/bro and /closing

/bro re-explains the last answer, or any text or ID, in plain words. /closing checks that a fresh session could resume from the files.

Spec page renderer

render-spec.sh and .ps1: one interactive review page per feature, nothing to install.

Files, not chat

specs/, tasks.json, history.md, decisions/answers.md, a project map, validation scripts and the sdd-update self-update skill.

Works with every harness

Same workflow and artifacts everywhere; only the packaging changes. Missing features fall back gracefully: roles instead of subagents, skills read on demand, rules instead of hooks.

Optional, never default

Ten skill packs, example hooks and MCPs. Nothing is installed or enabled without your selection.

context-audit · project-mapKeep the context window lean; refresh the project map.
run-and-verifyYour real dev, test, lint and build commands. Never invented.
dependency-freshnessCheck current docs before changing external APIs or SDKs.
git-disciplineCommit, PR and release text tied to tasks. Every git mutation asks first.
decision-log · documentation-updateDurable decisions in versioned files; docs current at task close.
failure-learningTurn real mistakes into lessons, proposed and never written silently.
ui-qa · spec-from-screenshotVerify UIs in a browser (Playwright scoped to one agent); turn screenshots into spec material.
Hooks · MCPsHarness-neutral example hooks and MCP notes, all off until you approve them.

Human-gated by design

  • Spec approval comes first. No production code before it.
  • Hooks and MCPs are off by default. Each one needs your approval.
  • Autonomy is read-only. Monitoring CI is fine; deploying, merging or marking tasks done never runs unattended.
  • Git mutations ask first. No commit, push or force-push without an explicit request.
  • No secrets in memory. Lessons and decisions are proposed; nothing is written without approval.
  • Nothing phones home. The default install is fully local, with no stored credentials.

Stay current, contribute

Updates

Watch the repository's releases on GitHub. In an installed project, invoke the sdd-update skill: it refreshes the kit files, merges your adaptations with approval and runs the migration notes from CHANGELOG.md.

Contributing

Fork, branch from main, one concern per PR. Keep files in English, templates on {{PLACEHOLDER}} syntax, hook scripts POSIX and jq-optional, installable files harness-neutral.
