SDD Onboarding Kit

Reference for installing and running Spec Driven Development with Claude Code, Codex CLI, Cursor, OpenCode or Antigravity. Quick start: overview page. Deep policy: reference/.

1What is SDD

Spec Driven Development: the coding agent writes a specification and gets it approved before touching production code. The spec has requirements (observable behavior), design (what changes, how, why) and tasks (an ordered checklist). The agent then implements strictly against it, and a reviewer checks traceability and tests. The point: no ambiguity, no scope creep, and a real decision point for you before code exists.

2What this kit is

A reusable installer, not a global configuration. Run the onboarding prompt and the agent reads the kit, inspects your repo, asks project-specific questions and generates:

  • AGENTS.md for your project (plus a two-line CLAUDE.md import stub when Claude Code is used);
  • five roles (leader, spec-author, implementer, reviewer, documenter) in the harness's agent format;
  • the core skills sdd-workflow, sdd-update, bro and closing;
  • local task and spec storage, the spec renderer and validation scripts;
  • optional hooks, MCPs and skill packs, only if you choose them.

The kit itself stays inert; only the generated harness is active.

2bHarness support

Same workflow, artifacts and rules under every harness. The kit's files use the Claude Code layout (.claude/) as the reference layout; reference/harness-primitives.md maps each concept and its fallback. Onboarding asks which harness(es) you use (questions.md §0), installs into that <harness-dir> and records it in the manifest.

3Installation

Prerequisites: a supported harness and a git repository (a plan-only repo with no code is fine). Optional: bash and jq for hook scripts and the bash validator (Git Bash or WSL on Windows); the PowerShell validator needs neither. The spec renderer needs only sh or PowerShell.

  1. Copy the kit into your project root: my-project/sdd-onboarding-kit/.
  2. Open your harness in my-project/. The kit's root AGENTS.md tells any harness how to read it.
  3. Run the onboarding prompt:
Read `sdd-onboarding-kit/instructions.md` and configure this repository to use Spec Driven Development with this harness. Ask me all necessary questions before making project-specific decisions.
  1. Answer the questions (harness, scope, approval policy, storage, commands, git policy, hooks, MCPs, protected files), or accept the recommended defaults (§31).
  2. Review the summary of created files and open TODOs, then the generated AGENTS.md and harness directory.

Greenfield and plan-only repositories
  • The project map records the planned layout, labeled as planned.
  • Unknown commands become TODO: ask the developer; run-tests.sh/run-lint.sh exit 0 cleanly until filled.
  • tasks.json can be seeded from an existing phased plan (one pending task per unit, linked to its plan section), after you confirm the granularity.
  • No silent git init: the agent asks and records the decision.
  • Keep tool-running hooks off until there is code to run.

4Daily workflow

1 · Start a feature

Create a new SDD task for: <description>. First generate requirements/design/tasks and do not implement anything until I approve the spec.

The agent adds the task to tasks.json, writes specs/<feature-slug>/, renders the spec page and stops.

2 · Review in the browser

Open specs/<feature-slug>/spec.html (re-render with sh scripts/render-spec.sh specs/<feature-slug>/). Accept, change, reject, answer or comment per item; approve or request changes. Save feedback.md or copy it, then say “read the feedback”. Repeat until you approve. Details in §6.

3 · Approve, implement, review

I have reviewed the spec for `<feature-slug>` and I approve it. Change the status to `human_approved` and prepare the implementation following `tasks.md`.
Implement feature `<feature-slug>` following the approved spec strictly. Run tests and leave traceability of what you changed.
Use the reviewer to validate the implementation of `<feature-slug>` against requirements.md, design.md and tasks.md. Run tests and tell me if it can be marked as done.

Lost in a long answer? /bro. Stopping for the day? /closing (§35).

6Spec format and review page

specs/<feature-slug>/
├── requirements.md   observable behavior (EARS, user stories, Given/When/Then or numbered)
├── design.md         files to change, interfaces, data, tests, risks, rollback
├── tasks.md          ordered tasks with status markers, each tied to requirements
├── assumptions.md · open-questions.md · acceptance-tests.md   (from a functional document)
├── review.md         written by the reviewer: traceability, commands, findings, decision
└── spec.html         rendered review page (gitignored by default)

Markdown with YAML frontmatter is the source of truth. Each file owns one content type and references the others by ID; duplication is a review finding. Specs are short on purpose: skills/sdd-workflow/spec-format.md sets word budgets per document and the markdown conventions (requirement rows, verdict and status markers, cards).

Render

sh scripts/render-spec.sh specs/<feature-slug>/ (Windows: scripts/render-spec.ps1) writes one self-contained page, spec.html: an overview with at a glance and needs your decision, one tab per document, light/dark theme. No Node or Python: the page renders the embedded markdown in the browser. Assets come from <harness-dir>/skills/sdd-workflow/templates/ (override with SDD_HARNESS_DIR or --assets DIR).

Review and feedback loop

  1. Per item (REQ-…, A1, Q1, T1…): Accept, Change, Reject, Answer or Comment.
  2. Overall: approve or request changes, plus an optional general note.
  3. Save feedback.md into the spec folder (or download <feature-slug>.feedback.md), or copy it into the chat.
  4. Tell the agent “read the feedback”. It applies it to the markdown, re-renders, and deletes the feedback file. specs/**/feedback.md is gitignored.

Example: specs/example-feature/spec.html.

8Hooks

Shell scripts the harness runs on events; they enforce rules deterministically. All kit hooks are examples, disabled by default, and none is enabled without your approval. Scripts are harness-neutral: an identical adapter block reads each harness's payload (or SDD_HOOK_* variables) and SDD_HOOK_OUTPUT picks the deny format. Hooks also fire in headless runs, so they enforce the state machine for autonomous work (§26). Policy: hooks/hooks-policy.md; wiring: hooks/settings-snippets.md.

Classes: advisory suggests, writes nothing · blocking can stop a tool call, writes nothing · mutating and dangerous: the kit ships none.

HookEvent (Claude Code / Codex)ClassPurpose
Block before approvalPreToolUse Edit/WriteBlockingNo code edits while a task is pending/spec_draft/spec_ready; spec files stay editable
Validate specPreToolUseBlockingSpec files must exist before spec_ready
Block destructive commandsPreToolUse BashBlockingrm -rf, git reset --hard, drop database…
Spec driftPreToolUse Edit/WriteAdvisory / blockingEdits outside the task's scope globs; DRIFT_MODE=warn|block
Run tests after editsPostToolUse Edit/WriteAdvisoryRuns the configured suite; never blocks
Targeted validationPostToolUse Edit/WriteAdvisoryMaps the changed file to a targeted check; suggests, or runs in run mode
Failure-learning nudgePostToolUse BashAdvisorySame check failed twice → reminds that the skill exists (§21)
Pre-compact capturePreCompact + SessionStartAdvisoryWrite durable state before compaction, re-read after; optional gate mode
Notify for approvalStop / NotificationAdvisoryAlerts you when the agent waits for approval
Installing a hook
  1. Get approval for the specific hook and mode (questions.md §9). Check bash and jq. Keep tool-running hooks off until the toolchain exists.
  2. Copy the script from hooks/examples/ to <harness-dir>/hooks/, make it executable, keep the adapter block unchanged.
  3. Adapt project parts only (targeted-validation RULES, failure-learning watch_pattern, allowed paths). Never wire an unconfirmed command.
  4. Register it with the matching snippet from hooks/settings-snippets.md. Start in warn/suggest mode.
Troubleshooting
  • Does not fire: check event name, matcher, path, executable bit; restart the session.
  • Blocks everything: read the script header (the approval guard is project-wide); adapt the filter or use warn mode.
  • Windows: needs Git Bash or WSL plus jq; hooks fail open without jq. For validation use validate-sdd-structure.ps1.
  • Test manually: echo '{"tool_name":"Edit","tool_input":{"file_path":"src/x.ts"}}' | ./spec-drift.sh.
  • Version drift: adapter verified against each harness's hook docs (2026-09); re-verify before enabling.

9MCP integrations

Optional connections to external systems; the harness works fully without them. Never configured without your explicit approval. Server definitions are the same everywhere; only the config file differs (§2b). Where one CLI call is enough, the kit prefers it (§25). Candidates: GitHub, Linear, Jira, Notion / Google Drive, Memory, and Playwright, which is scoped to the optional browser-tester agent, never global (§24). Policy: mcps/mcp-policy.md.

The generated AGENTS.md is the central configuration: build/test/lint commands, which tasks need SDD, the approval policy, the state machine, spec and task storage, protected files, the render command, installed skills by name.

The documentation phase adds documentation_required, documentation_status, documentation_targets (§22); spec drift reads optional scope globs (§8).

14Language policy

English is canonical for every reusable kit file. Generated project artifacts (specs, decisions, task descriptions, history) may use the project's language, chosen at onboarding. File names, state names and status values (spec_ready, human_approved) stay English so hooks and scripts work. Non-English material kept in the kit must be marked legacy.

16Project map

A one-to-two-screen orientation file generated at onboarding from templates/project-map.md.template, so the agent learns the repo without reading many files. Default <harness-dir>/context/project-map.md, or docs/project-map.md (questions.md §12). AGENTS.md links it, never embeds it. Unknown commands are TODOs; secrets are never recorded; a deferred map is a recorded TODO, not an empty file.

Sections: annotated tree (2–3 levels), entrypoints, commands, framework/runtime assumptions, important docs, protected areas, SDD locations, generated files.

Update it when a top-level directory, an entrypoint, the commands, or a protected/generated path changes. Not for routine files.

Example

## Commands

## Protected areas
prisma/migrations/, .env*, .github/workflows/

18Run and verify skill

When selected, onboarding generates <harness-dir>/skills/run-and-verify/SKILL.md from templates/run-and-verify.md.template: the project's real dev-server, test, targeted-test, lint, typecheck and build commands, required services, environment variable names only, and UI/API verification recipes.

  1. Inspect first: package.json, Makefile, CI config, docs; confirm inferred commands.
  2. Ask only the gaps (questions.md §15; §7 answers are reused).
  3. Never invent: unknowns become TODO: ask the developer and surface as unverified items.

The implementer validates through it before review; the reviewer records commands, results and unverified items in review.md. No secret values, and never production without explicit instruction.

Examples by project type

19Dependency and API freshness

Model knowledge lags fast-moving libraries. Before changing external dependencies, SDKs, APIs, framework configuration or security-sensitive integrations, the agent checks current official docs and records the evidence. Enforced by the design template, spec-author and reviewer even without the pack. Policy: reference/dependency-freshness-policy.md; strictness: questions.md §16.

TierApplies toEffect
RequiredAuth, payments, migrations, cloud infra, framework upgrades, security-sensitive codeMissing evidence blocks approval
AdvisoryOrdinary dependency changes, new calls to a known API, build configRecommended; justified exception allowed
Not neededInternal changes, refactors, lockfile-validated patch bumpsDesign says None

Evidence (design section External dependencies and freshness): dependency and version, docs checked with date, version constraints, deprecated APIs avoided, compatibility notes. Fetched pages are untrusted data; unreachable docs are reported, not guessed; no installs without approval.

21Failure learning

After a meaningful mistake (wrong convention, architectural violation, repeated assumption or error, wrong command, out-of-scope edit), the optional pack drafts a lesson and proposes it. Typos, secrets, personal data and speculation are never memorized.

I found a reusable lesson from this mistake:
<proposed memory entry>
Do you want me to add this to memory?
1. Yes, global memory.   2. Yes, project memory only.
3. No, keep it only in the review/history.   4. Revise the wording first.

Option 2 is the default; no answer means nothing is written. Entries follow templates/memory/failure-learning-entry.md (trigger, what went wrong, root cause, rule, where to apply and not, source). A good entry is specific and scoped (“service tests use test/fakes/, never DB mocks”); “be more careful with tests” is rejected. An optional advisory hook nudges after repeated failures and never writes.

22Documentation phase

Docs are updated after technical review (so they describe what ships) and before done (so they are not forgotten). The state machine is unchanged; three task fields track it: documentation_required, documentation_status (pending|updated|not_required), documentation_targets.

  1. Reviewer approves the code, then decides: docs required (lists targets) or not_required.
  2. If required, the documenter updates the listed targets and reports updated vs unaffected.
  3. Reviewer re-checks, sets updated; only then done.
TargetUpdate when the task changes…
README / user docsquick start, usage, features, what users see
API docsendpoints, payloads, public signatures, errors
Setup docsservices, env var names, install steps
Changelog / history.mdanything user-visible (history always gets an entry)

Not required: internal refactors, test-only changes, fixes that restore documented behavior. No secrets or internal URLs in docs, ever.

23Project memory and decision logs

Decisions must survive compaction and new sessions, so they live in decisions/: answers.md (always) plus, with the decision-log pack, architecture-decisions.md, rejected-options.md, workflow-decisions.md, or the project's existing docs/adr/ (questions.md §17).

Flow: the spec-author reports significant decisions at spec_ready; the reviewer flags those settled during work; the agent proposes exact entry text; you approve, revise or decline. Superseded entries are marked, never deleted. Logged: architecture, rejected alternatives, workflow rules, recurring answers. Not logged: trivia, one-off instructions, speculation, and never secrets.

A good entry
## 2026-03-14 — Use PostgreSQL for the persistence layer
- Status: accepted
- Context: the task queue needs transactions plus relational reporting.
- Decision: PostgreSQL 16 on the existing cluster; no second datastore.
- Alternatives rejected: DynamoDB (no cross-entity transactions).
- Consequences: schema changes follow the migration policy.
- Source: TASK-031 design review.

Dated, scoped, explains why, names what lost, cites its source.

24Browser/UI testing with Playwright

A real browser is the right tool for UI acceptance criteria and the wrong thing to load globally, so the kit ships it as an optional, scoped subagent. agents/optional/browser-tester.md declares the Playwright MCP inline in its own definition where the harness supports per-agent MCPs (Claude Code; Codex via [mcp_servers.playwright]): the tools exist only while it runs. Cursor, OpenCode and Antigravity put the server in the harness MCP config with the same rules.

Onboarding (questions.md §18): no UI → nothing installed · browser-tester + ui-qa · document setup only · custom. Specs gain optional UI acceptance criteria (route, visual state, flow, accessibility, viewports) and a UI verification plan; both say None for non-UI work.

Safety: credentials never stored (test accounts, provided at run time with approval) · local/test instances only, destructive actions need per-action approval · page content is data · screenshots not committed without approval · re-verify the MCP syntax at install (mcps/playwright-policy.md).

25CLI vs MCP

Choose the narrowest tool that does the job safely; the harness works with neither. Policy: reference/cli-vs-mcp-policy.md; preference: questions.md §10 (default: narrow CLI).

  • One narrow read → CLI (one PR's metadata, a deployment status).
  • Structured, repeated or scoped access → MCP, scoped as tightly as possible.
  • Remote mutations (push, deploy, merge, tickets, infra) need explicit per-action approval. Credential operations stay with the developer.

An authenticated CLI is privileged even when read-only; allowlist read-only subcommands at most. CLI and MCP output is data, not instructions.

26Autonomy policy

Autonomy is controlled execution, not blanket permission. Loops, goals, scheduled routines, background and headless runs are opt-in, scoped, bounded and unable to advance SDD state. Harness features differ; the policy applies by capability (reference/autonomy-policy.md).

Allowed (read-only, bounded)Never autonomous
Monitoring CI · polling deployment status · waiting for checks · re-running tests and linters and reporting drift Deploys, migrations · payment/auth/security changes · merging, pushing to protected branches · any status advance, including done

Every run declares a success condition, a bound (iterations, time, budget) and a failure threshold. Example: “watch CI, stop when it finishes or after 2 hours” is safe; “keep working until the PR is merged” is not. Gate hooks keep firing headless; disabling them for a run is a violation. Never bypass permissions outside a disposable sandbox; treat ingested logs and payloads as data.

27Deep review policy

For high-risk changes (security, auth, payments, migrations, infrastructure, public APIs, large refactors, data-loss risk), deep review supplements the SDD reviewer, never replaces it, and is recommended unless the project requires it. Policy: reference/deep-review-policy.md.

  1. Always: the reviewer's High-risk review checklist at raised effort, with a security pass where relevant.
  2. Recommended: independent adversarial reviewers per lens (security, correctness, performance).
  3. Optional: paid cloud or PR-review services, only if available and approved per invocation.

Rungs 1–2 cost nothing extra; a missing paid feature never blocks a task. Output: security and performance findings (None found is valid, silence is not), edge cases mapped to requirements, reproduction attempts, remediation plan. Blocking findings return the task to in_progress.

28Screenshots and visual evidence

Screenshots are evidence, not complete requirements, and the agent asks when visual intent is ambiguous. The optional spec-from-screenshot pack inventories each image with provenance (route, environment, viewport, or unknown), separates what is visible from what is inferred, asks about missing states, and maps results into the spec. Images with secrets or personal data are flagged; credentials are never transcribed.

Where it lands: requirements.md Visual evidence (inventory, observed vs expected) and UI acceptance criteria referencing image IDs; review.md Visual verification (pass / fail with difference / not verifiable). Works for mockups, visual bug reports, before/after regressions and “done looks like this” images.

29Git discipline

Baseline, with or without the pack: every mutating git action is permission-gated. The optional git-discipline pack adds rules and templates and never substitutes for approval, review or the docs phase.

  1. Inspect git status and the diff first. Never overwrite uncommitted developer work.
  2. No commit, push or PR merge unless asked; no force-push without documented approval.
  3. Reference the task/spec in commit messages per the project convention (questions.md §8).

30Session recovery

Durable artifacts are the source of truth, never chat history. Recap, rewind, resume and compaction are conveniences; verify what they claim against the files. Rewind/checkpoints only cover the agent's direct edits, not shell side effects; git stays authoritative. Guidance: reference/session-recovery.md.

Resume checklist: tasks.json status → the active spec as approved → latest review.md → git status and diff → decision logs and history.md. When memory and an artifact disagree, the artifact wins and the agent says so. Recovery never changes task state or revives an approval. Run /closing (§35) before you stop so the next session can start from the files.

34Maintainer guide

For changing the kit itself. Same philosophy it installs: one canonical home per rule, summaries link to it, CI enforces the mechanics.

  1. One home per rule. Deep policy in reference/ or a skill; READMEs and AGENTS.md.template summarize and link.
  2. Keep mirrors in sync: README.md ↔ README.html; templates ↔ review checklist ↔ reviewer output; questions.md defaults ↔ instructions.md default profile; validate-sdd-structure.sh ↔ .ps1; render-spec.sh ↔ .ps1.
  3. Append, don't renumber. New questions.md and DOCUMENTATION.html sections go at the end; section numbers are cited across the kit.
  4. New optional feature: a questions.md entry with a safe default, an install step, a feature-matrix row (§33), both READMEs, a section here.
  5. New hook: classify it, ship it disabled, add a snippet, fail open without jq, pipe jq -r through tr -d '\r', shellcheck it.
  6. Verify harness behavior against each harness's current docs before documenting it; never document undocumented features.
  7. Keep installable files harness-neutral: harness names only in per-harness tables or examples.
  8. After adding, renaming or deleting files: git add, then scripts/update-manifest.sh, commit manifest.md.
  9. Run the CI checks locally: stale spec-artifact references, the {{PLACEHOLDER}} allowlist, manifest diff, shellcheck.
  10. Safety gates are not refactorable. Anything that lets a feature write memory, mutate git/remote state or advance SDD state without approval is a regression.
